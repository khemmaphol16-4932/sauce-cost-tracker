### Map E — Sale lifecycle

**Log** (`sales/actions.ts:20–92`)
1. `getRecipeDetail` (5 queries) → `calcRecipeCost` in TS.
2. `INSERT sales` — the BEFORE INSERT trigger `deduct_finished_goods_on_sale` fires *inside* this statement and, per `0016`, **either** decrements `finished_goods_stock` **or** decrements raw `ingredients` (made-to-order branch), **blocking on shortfall in both branches**.
3. **Separately, after the insert commits** (`:78–87`), the app inserts `sale_ingredient_usage` rows — *only if* `is_made_to_order && ingredients.length > 0`.

Steps 2 and 3 are **not in one transaction**.

**Edit** (`:94–123`) — writes `payment_status`, `payment_method`, `sale_date`, `customer_ref`, `notes` only. Explicitly refuses to touch `qty_bottles`/`recipe_id` (comment at `:106–108`). **Reverses nothing, restores nothing.** No stock implication today.

**Delete** (`:125–178`)
1. Read `sales.recipe_id, qty_bottles`.
2. Read `sale_ingredient_usage` for the sale (**before** deleting — it would cascade away).
3. `DELETE sales` — cascades away `sale_ingredient_usage`.
4. **Branch on `usage.length > 0`**: if rows existed, loop and restore each ingredient with read-then-write; else call `adjust_finished_goods_stock(+qty_bottles)`.

The reversal reads the `sale_ingredient_usage` snapshot. The **mode is inferred from the snapshot's existence**, not from `recipes.is_made_to_order`. See **F4**.

## Findings

### F1 — Made-to-order sales **block** on shortfall, directly violating settled decision A3
**Severity:** correctness
**Confidence:** confirmed (`supabase/migrations/0016_made_to_order_recipes.sql:59–74`)
**Evidence:**
```sql
if is_mto then
  select string_agg(...) into shortfalls
  from recipe_ingredients ri join ingredients i on i.id = ri.ingredient_id
  where ri.recipe_id = new.recipe_id
    and i.qty_on_hand < ri.qty_used * new.qty_bottles;
  if shortfalls is not null then
    raise exception 'Not enough stock to log this sale: %', shortfalls
      using errcode = 'P0001';
  end if;
```
Decision A3 states: *warn, allow the sale, let stock go negative, and flag the ingredient for reconciliation.* The implemented trigger does the opposite — it aborts the INSERT.
**Impact:** the operator sells a noodle set, the fridge count is stale by 20g of scallion, and the app **refuses to record a sale that has physically already happened.** The rationale in A3 is exactly right: the workarounds (faking a purchase, or not logging the sale) corrupt the data worse than a negative balance. This is live in the production database now; it is dormant only because no recipe has `is_made_to_order = true` in prod yet, and it activates the moment `1367cf3` deploys. Given made-to-order is the majority of sale volume, this will fire regularly.
**Fix sketch:** in the made-to-order branch, drop the `raise exception` and always apply the decrement. Return the shortfall list to the caller as a non-fatal warning (e.g. via a `RETURNS` payload on an RPC, or let the app pre-check and surface a warning banner). Keep the batch branch (`deduct_stock_on_batch`) blocking — the two paths intentionally differ. Requires **F6** (negative-stock surface) to land with it or immediately after, or the negatives become invisible.
**Effort:** S (trigger change) + M (warning UX)
**Depends on:** F6 must ship in the same release or the data silently rots.

### F2 — `deleteSale` deletes the sale **before** restoring stock, with no transaction — a failed restore is unrecoverable
**Severity:** data-loss
**Confidence:** confirmed (`src/app/sales/actions.ts:147–166`)
**Evidence:** the DELETE is at `:147`; the restore loop is at `:159–166`. Between them the `sale_ingredient_usage` rows have already cascaded away (`0016:19` `on delete cascade`), and they were only held in a local JS variable read at `:141–144`.
```ts
const { error: deleteError } = await supabase.from("sales").delete().eq("id", id);   // :147
if (deleteError) return { error: deleteError.message };
if (usage && usage.length > 0) {
  ...
  for (const u of usage) {                                                            // :159
    const { error: restoreError } = await supabase.from("ingredients")
      .update({ qty_on_hand: current + u.qty_used }).eq("id", u.ingredient_id);
    if (restoreError) return { error: restoreError.message };                         // :165 — bails mid-loop
  }
}
```
**Impact:** a noodle set has ~11 ingredients, so this is an 11-iteration loop of separate HTTP round trips. If the phone loses signal on iteration 6 (entirely plausible mid-service), the outcome is: sale row **gone**, snapshot rows **gone**, ingredients 1–5 restored, 6–11 not. There is no record left of what was supposed to be restored and no way to retry. Stock is silently wrong forever. `deleteBatch` (`batches/actions.ts:159–193`) has the same loop but happens to order it more safely (restore, then delete) — there a mid-loop failure leaves the batch intact, so a retry double-restores instead. Both are wrong; `deleteSale` is the destructive one.
**Fix sketch:** move the whole reversal into one `security definer` SQL function that takes the sale id, restores from the snapshot with a single set-based `UPDATE … FROM sale_ingredient_usage`, and deletes the sale — one statement, one transaction, atomic by construction. This is also the fix for F3.
**Effort:** M
**Depends on:** —

### F3 — `ingredients.qty_on_hand` is written with read-modify-write in two server actions; the RPC that exists to prevent exactly this was never extended to ingredients
**Severity:** correctness
**Confidence:** confirmed (`src/app/sales/actions.ts:158–164`, `src/app/batches/actions.ts:173–179`)
**Evidence:** both build a `Map` of previously-read quantities and then write an absolute value:
```ts
const qtyById = new Map((ingredients ?? []).map((i) => [i.id, i.qty_on_hand]));
const current = qtyById.get(u.ingredient_id) ?? 0;
await supabase.from("ingredients").update({ qty_on_hand: current + u.qty_used })...
```
Compare `0013_atomic_stock_adjust.sql:1–12`, which introduced `adjust_finished_goods_stock` specifically because *"That pattern has a lost-update race … the write uses a value read earlier, not a live increment."* That reasoning was applied to `finished_goods_stock` and stopped there. Grep confirms no `adjust_ingredient_stock` function exists.
**Impact:** the window is real in this app — the restore loop makes 11 sequential round trips, so it is open for hundreds of milliseconds. Any concurrent write to the same ingredient during that window is silently discarded. Concurrent writers exist: the purchase trigger (A1), the waste trigger (A3′), and the sale trigger (A4). Logging a purchase on the phone while a void is mid-loop loses the purchase's quantity. Low frequency for a single operator, but the failure is silent and undiagnosable after the fact.
**Fix sketch:** add `adjust_ingredient_stock(p_ingredient_id uuid, p_delta numeric)` mirroring `adjust_finished_goods_stock` (ownership check, in-database increment), or fold it into the atomic reversal function from F2. F2's set-based `UPDATE … FROM` fixes both at once and is the better shape.
**Effort:** S (if merged with F2)
**Depends on:** F2 (same fix)

### F4 — Void routes on snapshot *existence*, so a made-to-order sale with no snapshot credits phantom bottles to `finished_goods_stock`
**Severity:** correctness
**Confidence:** confirmed (`src/app/sales/actions.ts:150,167–172` vs `:78`)
**Evidence:** the write guard is `if (detail.recipe.is_made_to_order && detail.ingredients.length > 0)` (`:78`) but the read branch is `if (usage && usage.length > 0)` … `else { adjust_finished_goods_stock(+qty_bottles) }` (`:150,167`). The two conditions are not inverses.
**Impact:** two concrete ways to diverge. (1) A made-to-order recipe with **zero ingredients** — easy to create, e.g. a recipe stubbed out before its ingredient list is filled in — writes no snapshot, so voiding it credits `finished_goods_stock` for a recipe that has no finished goods, inventing bottles from nothing. (2) The `sale_ingredient_usage` insert at `:79–86` runs **after** the sale insert has already committed and its trigger has already decremented raw stock; if that insert fails (network, RLS), the ingredients are deducted with no snapshot, and the later void credits phantom bottles *and* never restores the real ingredients. Both leave `finished_goods_stock` positive for a made-to-order recipe, which then feeds the "Bottles in stock" card on `/stock` (`stock/page.tsx:38–47`).
**Fix sketch:** branch on `recipes.is_made_to_order` read alongside the sale row, not on snapshot presence. Treat a made-to-order sale with a missing snapshot as an explicit error rather than silently falling through to the finished-goods path.
**Effort:** S
**Depends on:** F2 (touches the same function)

### F5 — `logSale` deducts stock in a trigger, then writes the audit snapshot in a separate uncommitted-together statement
**Severity:** correctness
**Confidence:** confirmed (`src/app/sales/actions.ts:52–87`, `0016:75–79`)
**Evidence:** the `INSERT sales` at `:52–70` fires the BEFORE INSERT trigger that decrements `ingredients`. The `sale_ingredient_usage` insert is a *second* statement at `:79–85`. There is no transaction wrapping them; `supabase-js` issues each as its own PostgREST request.
**Impact:** the deduction and the record of what was deducted can diverge. This is the same shape as F4's case (2) but worth its own line because the fix is different: F4 fixes the *read* side, this fixes the *write* side. `logBatch` has the identical structure (`batches/actions.ts:41–65`) and the identical exposure.
**Fix sketch:** have the trigger itself write the usage rows (it already computes exactly those quantities at `0016:76–79`), which makes deduction and snapshot atomic by construction and removes the TS-side multiplication at `:83` entirely — also closing the TS↔SQL divergence noted in Map B and H4.
**Effort:** M
**Depends on:** —

### F6 — There is no surface anywhere for negative or unreconciled stock
**Severity:** correctness (it is the mechanism that keeps A3 from rotting the data)
**Confidence:** confirmed (`src/app/stock/page.tsx:14–20`, `src/app/stock/ingredient-row.tsx:83`, `src/app/stock/low/page.tsx:11–16`)
**Evidence:** every "is this bad?" check in the app is `qty_on_hand < low_stock_threshold`, and `low_stock_threshold` is nullable (`0001:17`) and unset by default. An ingredient at `-50` with a null threshold is excluded from the low-stock count at `stock/page.tsx:14–16`, excluded from `/stock/low` at `low/page.tsx:11–13`, and rendered as plain body text by `ingredient-row.tsx:83` (`{ingredient.qty_on_hand} {ingredient.unit} on hand`) with no colour, badge, or ordering change.
**Impact:** decision A3 deliberately allows stock to go negative, on the premise that the flagged list is what prompts the operator to log the missing purchase. That list does not exist. Ship A3 without this and negative balances become invisible — the failure mode A3 was designed to avoid (silent data rot) arrives anyway, just by a different route. This is why F1 and F6 must ship together.
**Fix sketch:** derive it — no new state needed. `qty_on_hand < 0` is the condition; surface it as a distinct high-contrast band at the **top** of `/stock` (not `/stock/low`, which is a separate tab the operator won't open mid-service), with a one-tap "log the purchase" affordance that opens the existing purchase modal for that ingredient.
**Effort:** S
**Depends on:** blocks F1

### F21 — The purchase log is being used as a stock-adjustment tool, and every such entry corrupts `avg_price_per_unit` (**measured in live data**)
**Severity:** correctness / data-quality
**Confidence:** confirmed — measured against the production database 2026-08-18
**Evidence:** there is no way to correct a raw-ingredient count in this app. `adjustFinishedGoods` exists for bottles (`src/app/sales/actions.ts:213–232`) but there is **no equivalent for `ingredients`** — the only control that changes `qty_on_hand` from the UI is "+ Purchase" (`src/app/stock/ingredient-row.tsx`), and that form requires a price. So corrections get logged as purchases with a placeholder price. Live query:

```
select … from purchases where price_paid_total <= 2   →  9 rows, all 2026-08-17, all price_paid_total = 1
  เนื้อ ปูอัด                 905 g for ฿1   → ฿0.0011/g
  ผัก กะหล่ำปลีลอกขาว          100 g for ฿1   → ฿0.0100/g
  ผัก ข้าวโพดหวาน แช่แข็ง       30 g for ฿1   → ฿0.0333/g
  ผัก แครอทหั่นเต๋าแช่แข็ง       30 g for ฿1   → ฿0.0333/g
  … 5 more
```
**Impact:** this is the actual cause of the wrong costs, and it is far more damaging than F7's slow drift. `recalc_ingredient_on_purchase` (`0001:70–74`) folds every one of these into the weighted average **permanently**. Measured effect on the four worst ingredients right now:

| Ingredient | app uses now | most recent real price | understated by |
|---|---|---|---|
| เนื้อ ปูอัด | ฿0.1701/g | ฿1.70/g (100 g for ฿170, Aro) | the ฿1/905 g row drags the average down ~50% |
| หมู สันนอกหมูสดสไลด์ | ฿0.1573/g | — | −87% vs. last entry |

| หมู สะโพกหมูหั่นแช่แข็ง | ฿0.1133/g | ฿0.118/g (1000 g for ฿118) | −82% vs. last entry |

Every one of those feeds `calcRecipeCost` → `cost_per_bottle_snapshot` → reported margin. The app is currently telling you your ingredients are cheaper than they are, which means **reported margins are too optimistic** — the direction that loses money.
**Fix sketch:** add an ingredient stock adjustment that writes `qty_on_hand` **without** touching `avg_price_per_unit` and without inserting a `purchases` row — mirroring the existing `adjustFinishedGoods` shape, with a reason field. **Effort:** S (the adjustment action) + S (one-off data cleanup)
**Depends on:** pairs naturally with F6 — a negative-stock prompt needs somewhere to send you, and "adjust the count" is that destination

### F7 — `avg_price_per_unit` is a **lifetime** weighted average — a real design flaw, but currently **not** the thing distorting your numbers
**Severity:** correctness (latent)
**Confidence:** confirmed (`supabase/migrations/0001_init.sql:70–74`); **impact measured and found to be nil today**

> **Correction to my own ranking.** I originally ranked this #3 on the reasoning that "every margin is priced off months-old purchases." I tested it against the live data and that is **not true yet**. No ingredient has more than **3** purchases: 5 ingredients have 3, 5 have 2, 12 have 1. Trailing-3 is therefore *mathematically identical* to lifetime for every single ingredient — the comparison returned 0.0% divergence across the board. F7 is a problem you will have, not one you have. **F21 is the one you have.**

**Evidence:**
```sql
avg_price_per_unit = (
  select sum(price_paid_total) / nullif(sum(qty_bought), 0)
  from purchases
  where ingredient_id = new.ingredient_id   -- no date filter, no window, no limit
)
```
**Impact:** this is the number `calcRecipeCost` multiplies by `qty_used` (`costing.ts:38`) to get raw material cost, which becomes `cost_per_bottle_snapshot` on every sale (`sales/actions.ts:65`), which is what `calcSaleMargin` and the dashboard's `realMarginTrend` report as profit (`dashboard.ts:274–283`). Under made-to-order — the majority of volume — **every noodle set's recorded margin is derived from this value at sale time.** A pork price rise in month 3 is diluted by months 1–2 forever; the app will keep reporting a healthy margin while the real one erodes. The dilution gets *worse* over time as history accumulates, so the number silently drifts further from reality the longer the business runs. This is a money-losing failure, not a cosmetic one.
**Fix sketch:** trailing-N (N=3) weighted average for costing, lifetime retained for Financials spend reporting. **Do not use "last purchase price"** — F21 proves why: with placeholder and mis-keyed rows in the log, last-price would swing costs by −80% to −99% on a single bad entry, whereas a trailing average dilutes it. Implement *after* F21, because F21 removes the noise that makes any averaging basis look broken.

### F15 — `yield_ratio` conflates "cooked less" with "yielded less", so spillage now silently **under**-deducts
**Severity:** correctness
**Confidence:** confirmed (`src/app/batches/actions.ts:36`, `0015:44–46`)
**Evidence:** `const yieldRatio = cost.bottlesPerBatch > 0 ? actualYieldBottles / cost.bottlesPerBatch : 1;` — the *only* input is bottles produced. Nothing in `batches` records how much of the recipe was actually cooked.
**Impact:** the hypothesis is correct and the direction matters. When the operator deliberately cooks a half batch, scaling is right. When a **full** batch is cooked and bottles are lost to spillage or over-reduction, the ingredients were fully consumed but the app now deducts only `yield/estimate` of them — stock reads higher than the fridge. Before `eb1d797` the bug was over-deduction, which shows up as stock running out early and gets noticed. Defence-in-depth gap, not currently exploitable by this single operator.
**Fix sketch:** separate the two quantities — record *batch scale* (how much of the recipe was cooked, defaulting to 1) as the deduction driver, and keep `actual_yield_bottles` as the finished-goods driver. The gap between `scale × estimate` and `actual_yield` is yield loss, which is worth surfacing on the existing `YieldVarianceCard` and makes true cost-per-unit computable. Also removes the need for the `bottlesPerBatch === 0` fallback in this path.
**Effort:** M
**Depends on:** F10 (touches the same cost basis question)
